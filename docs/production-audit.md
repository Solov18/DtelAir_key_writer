# Production-аудит многопользовательской работы

## Исправленные риски

- Непустой HEX теперь защищён глобальным PostgreSQL unique index без учёта
  регистра; номер остаётся уникальным внутри типа ключа.
- Логин защищён case-insensitive unique index, согласованным с авторизацией.
- Создание ключей, пользователей и ролей преобразует `IntegrityError` в
  понятную прикладную ошибку без 500 и без утечки SQL.
- Выдача ключа сотруднику, выдача УК, изменение/освобождение назначения и
  редактирование ключа блокируют целевую строку `FOR UPDATE`.
- Удаление, отключение и понижение последнего администратора сериализованы в
  одной транзакции с блокировкой активных администраторов.
- Общая запись физического ключа использует PostgreSQL advisory lock по ID
  ключа. После ожидания повторно читается список известных панелей, поэтому
  разные worker не отправляют один и тот же запрос одновременно.
- SQLAlchemy pool ограничен (`5 + 2` на worker, timeout 30 секунд,
  `pool_pre_ping`, recycle и LIFO), что даёт предсказуемую нагрузку на БД.
  Advisory-lock записи использует отдельные непулируемые соединения и локальный
  лимит 2 на worker, чтобы ожидание внешней CRM не занимало основной pool.

## Несколько worker

Cookie-сессия подписана общим `SESSION_SECRET`; права, роли, runtime-настройки,
назначения, журнал и прогресс мониторинга хранятся в PostgreSQL. Критичного
изменяемого состояния только в памяти worker нет.

Каждый worker может запустить scheduler, но только один удерживает session-level
PostgreSQL advisory lock мониторинга. Остальные не выполняют цикл. Состояние
цикла и heartbeat лежат в `panel_monitor_state`; динамические интервалы и
лимиты — в `system_settings` и читаются перед каждым циклом.

## Транзакции и редактирование

Каждый repository context `db()` создаёт SQLAlchemy Session, фиксирует весь
успешный блок одной транзакцией и делает rollback при исключении. Операции с
ключом сериализованы. Для обычных независимых полей сотрудника/панели действует
последняя успешно зафиксированная версия; уникальные и ссылочные ограничения
при этом не нарушаются. Optimistic version column не добавлялась, чтобы не
менять существующую UX/бизнес-логику.

Физический HTTP-вызов и локальная запись результата принципиально не могут быть
одной ACID-транзакцией с внешней CRM. Поэтому результат каждой панели
фиксируется отдельно, частичный успех сохраняется, ошибки доступны для повтора.

## Производительность

Списки используют серверную пагинацию/aggregate SQL. Контексты ключей и панелей
получаются пакетными запросами; запрос на строку таблицы не обнаружен в
основных реестрах. Рекомендуется начать с 3 worker. Обычный максимум — 21
pool-соединение, абсолютный максимум с шестью write-lock соединениями — 27;
это оставляет стандартному PostgreSQL запас для Alembic, backup и
администрирования.

После развёртывания следует наблюдать `pg_stat_activity`, медленные запросы,
память worker и журнал pool timeout. Увеличивать worker/pool без измерений не
рекомендуется.

## Ограничения и осознанные решения

- Новая migration не удаляет конфликтующие legacy-строки автоматически, а
  останавливается; перед upgrade обязателен read-only preflight.
- Backup хранится на том же сервере по требованиям базовой конфигурации.
  Для защиты от потери диска нужна дополнительная зашифрованная off-host копия.
- PostgreSQL advisory lock сериализует запись одного ключа, но разные ключи
  могут записываться параллельно (не более двух на worker), чтобы не исчерпать
  небольшой пул и не перегрузить CRM.
- Реальные панели и внешняя CRM во время аудита и тестов не вызывались.
